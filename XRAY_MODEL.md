# XRAY_MODEL.md — what the deployed model is, and what we can observe

Facts below were verified against the deployed code (not the papers). Citations
are `file:line`; `modeling_pi05.py` refers to the installed LeRobot copy at
`venv_lerobot/.../lerobot/policies/pi05/modeling_pi05.py` (lerobot 0.4.4).

## 1. The model

- **Architecture family:** π0.5 — a VLA with a PaliGemma VLM backbone
  (SigLIP vision tower, patch 14 → 16×16 = 256 tokens per 224×224 view;
  Gemma-2B language model, 18 layers / 8 heads) plus a **Gemma-300M action
  expert** (18 layers / 8 heads, width 1024) conditioned with adaRMS
  (`modeling_pi05.py:306-328`).
- **Action head type: flow matching.** Actions are generated by Euler
  integration over `num_inference_steps = 10`
  (`configuration_pi05.py:45`; confirmed in the checkpoint config).
  The loop is `PI05Pytorch.sample_actions` (`modeling_pi05.py:780-857`):
  the image+language prefix is embedded once and run through the LM with a KV
  cache, then `for step in range(num_steps)` (:824) calls `denoise_step`
  (:859) and integrates `x_t = x_t + dt * v_t` (:852).
- **Chunk:** 50 actions × 7 dims (Δxyz 3, Δaxis-angle 3, gripper 1). The
  wrapper executes the first **5** and replans
  (`policy/lerobot_pi05_policy.py:60,161-173`).
- **Checkpoint:** `lerobot/pi05_libero_finetuned_v044`, bf16
  (vision embeddings + layernorms kept fp32).
- **Normalization:** MEAN_STD for state and action, applied/undone by the
  checkpoint's pre/post-processors; the 7-D actions leaving `act()` are
  already in sim units.

## 2. What is extractable with READ-ONLY hooks

| Internal | How | Cost |
|---|---|---|
| Raw 50×7 action chunk | Already computed; `act()` slices it. New `act_with_internals()` returns the full chunk. | free |
| Per-step denoising estimates `x_t` (10×50×7) | Observe `x_t` after each Euler step in `sample_actions` (`modeling_pi05.py:852`). Plain Python — the wrapper sets `compile_model=False` (`policy/lerobot_pi05_policy.py:103`). | free (observation only) |
| Instruction↔image attention (prefix LM) | `language_model.config.output_attentions = True` before the prefix forward (`modeling_pi05.py:447-454`). 18 layers × 8 heads × 968². | ~120 MB/chunk if all layers kept — pool in-place and discard |
| Action→image attention (expert suffix) | `gemma_expert.model.config.output_attentions = True` (`modeling_pi05.py:459-466`). Per denoise step ≈ 8 heads × 50 × 1018. | ~15 MB/step — pool and discard |
| Image tokens | 256 per view, row-major 16×16 grids | n/a |

**No SDPA gotcha:** the inference path already forces eager attention
(`modeling_pi05.py:811` for the LM, `:881` for the expert), so enabling
`output_attentions` materializes weights without changing the compute path or
numerics.

**Prefix token layout** (`embed_prefix`, `modeling_pi05.py:634-680`; verified
against code): images are embedded in `config.image_features` order, then
language. The checkpoint has `empty_cameras=1`, so a fully pad-masked image
block sits between wrist and text:

```
[agentview 0-255] [wrist 256-511] [empty_camera pad 512-767] [text 768-967]
```

Prefix length is always 768 + 200 = **968**. Heatmap indexing that forgets
the empty block reads the wrong tokens — silently. All prefix attention is
bidirectional (`att_masks = 0`).

## 3. Camera parameters at runtime

`live/session.py:95-122` (`CameraGeometry`) already implements both
directions, reading intrinsics/extrinsics from the live mujoco sim — nothing
hardcoded:

- intrinsics: `f = (RENDER/2) / tan(fovy/2)` from `model.cam_fovy[cam_id]`;
- extrinsics: `data.cam_xpos[cam_id]`, `data.cam_xmat[cam_id]` (refresh per
  step; the camera is static but we re-read anyway);
- `world_to_display(p)` → stream pixel (accounts for the 640² render →
  640×480 center crop), `display_to_ray(x, y)` → world ray (validated by the
  click-to-push debug overlay in M2).

End-effector pose per step: `wrapper._raw["robot0_eef_pos"]` /
`["robot0_eef_quat"]` (raw robosuite obs retained by `sim/wrapper.py`).

## 4. Where the replan ticks are

- Live mode: `live/session.py`, `_run_episode` loop — `chunk = self.policy.act(...)`
  then `for action in chunk:` execution. Viz hooks attach here only.
- Space (phase 2): `space/app.py:221-235`, `infer_chunk` + execution loop.

X-Ray computation happens on these ticks, never per video frame, and never
between policy output and sim step (observation of tensors, not mutation).

## 5. Octo backend note

The live mode also supports the Octo backend (`WEBVLA_POLICY=octo`). X-Ray's
model-internal visualizations (denoising, attention) are **π0.5-only** in this
milestone; Octo sessions get the action overlay/bars/timeline only (those
consume the action chunk, which both backends produce).
